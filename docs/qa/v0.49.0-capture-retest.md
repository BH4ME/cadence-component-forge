# v0.49.0 Capture 放置复测（2026-11-12）

本轮已有 **4 个独立案例通过真实面板触发、官方 API 提交位置、保存及独立 Dbo 重开**。安装的产品仍为 `0.49.0-3a2c3f5def8e`，复测没有修改生产代码或安装包。初始带执行跟踪的诊断出现了经对话框确认的原生崩溃，作为失败案例保留在下表，根因尚未确定。此报告不代表鼠标落点验收，也未关闭 Allegro 原生稳定性问题，v0.49.0 继续保持预发布。

环境：Windows x64，Capture 17.4 S039；元件 `C2053170 / STM32F031F6P7TR`，20 引脚。四个完成案例运行于**同一个 Capture 会话**，使用不同独立工程及已有本地资源缓存；它们不属于四次冷启动。完整结构化结果见 [JSON](v0.49.0-capture-retest.json)。

时间以测试脚本点击搜索为起点，是累计响应偏移，包含步骤间人为加入的 150 ms 等待；不是各步骤单独耗时，也不能当作首次联网查询的速度保证。`PlaceNew` 返回只说明交互放置已启动，不等于元件已落在图纸上。

含旧实例的工程读回为 U1、U2、U3、U4：旧 U1–U3 保留原来的大写 `PCB Footprint` 属性，新 U4 使用小写属性，四个实例均有 20 个引脚和正确型号。此项验证限定为这份独立工程副本。

## 如何验证放置

1. 在独立工程中，经实际 Capture 内嵌 CEF 面板点击搜索、结果行和放置按钮，记录生产代码发回的 `place` 响应。
2. 测试脚本取消交互放置，再用官方 `PlacePart` API 在固定位置提交一个实例，赋予唯一位号并保存。位号由测试脚本赋值，这不属于产品自动标注验收。
3. 单独启动 Dbo 读取会话，重新打开已保存 DSN 和 OLB，检查实例数量、位号唯一性、型号、20 个引脚编号和 `PCB Footprint` 属性。新实例应使用实际小写 PSM 名称。

截图和鼠标输入通道仍不可用；本轮键盘 Escape 操作成功。没有将上述 API 提交等同于真实鼠标点击落点。所有变更限于独立测试工程，结束时再次核对两个原始工程的 4 个 OPJ/DSN 文件，**4 / 4 的 SHA-256 均与测试前一致**。

## 测试脚本回调查证

产品 `PlaceNew` 返回后，测试脚本的自动提交回调没有到达；外部 replay 驱动随后完成提交。静态检查发现 Cadence 的 hosted `nativeCall` 包装器会在 Tcl 命令末尾追加 `hostedClientId`，而 QA 的 `uiPlacementReturned` 原定义为零参数。产品请求处理器已有可选 `clientId` 参数。

在旧工程兼容案例中，仅将 QA 回调改为接收 `args`，实际桥接随后记录了 `ui_place_returned=1` 和 `hosted_client_argument_count=1`，确认漏接了一个宿主参数。这个测试脚本问题已定位；它不能用于解释更早的 `PlaceNew` 未返回或原生崩溃，也不需要据此修改产品放置代码。提交仍由外部 replay 驱动执行并独立读回。

## OLB 独立审计

旧、新 OLB 均为 51,712 字节；原生读取到的包、器件、符号、20 个引脚拓扑和顺序一致。官方 XML 导出只出现路径、时间戳和三处 PCB Footprint 大小写的差异，显式归一化这些字段后 XML 完全相同，读取前后原文件 SHA-256 不变。部分二进制差异未被 XML 表达，不能据此证明所有运行中设计缓存状态均有效。

## 仍未关闭的项目

- 初始带执行跟踪的诊断未收到 `PlaceNew` 返回，随后 CUA 实际读到 Capture 的 `This application has quit unexpectedly` 对话框，确认原生崩溃。故障模块与根因未知；后续成功不足以认定执行跟踪、保存弹窗或其他 UI 状态为根因。
- 真实鼠标落点和完整人工交互尚未验证。
- [Allegro 10 轮测试](v0.49.0-pcb-placement.json)仍保留 8 成功、2 失败；Capture 的成功不覆盖这些偶发故障。
- 尚无 Capture 17.2 实机及独立干净客户环境验证。

报告只公开脱敏结果与本地证据文件的 SHA-256，不包含用户名、绝对路径、进程编号或供应方 CAD 文件。原发布的其他测试范围见 [v0.49.0 发布记录](../releases/v0.49.0.md)。
