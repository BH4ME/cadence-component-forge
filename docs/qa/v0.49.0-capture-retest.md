# v0.49.0 Capture 放置复测（2026-11-12）

本轮已有 **4 个 API 提交案例通过保存及独立 Dbo 重开**，另有 **1 个由用户实际鼠标落点的案例通过保存和独立读回**。两类结果分别计数。安装的产品仍为 `0.49.0-3a2c3f5def8e`，复测没有修改生产源文件或安装包。初始带执行跟踪的诊断出现了原生崩溃，作为失败案例保留。随后首次建库专项又复现了两次无跟踪崩溃，并通过路径归一化对照验证修正；结果单独记录在 [v0.49.1 放置验证](v0.49.1-capture-placement.md)，不混入本报告原有成功数量。v0.49.0 的历史预发布状态保留。

环境：Windows x64，Capture 17.4 S039；元件 `C2053170 / STM32F031F6P7TR`，20 引脚。四个 API 案例运行于**同一个 Capture 会话**，使用不同独立工程及已有本地资源缓存；它们不属于四次冷启动。人工鼠标案例单独记录。完整结构化结果见 [JSON](v0.49.0-capture-retest.json)。

时间以测试脚本点击搜索为起点，是累计响应偏移，包含步骤间人为加入的 150 ms 等待；不是各步骤单独耗时，也不能当作首次联网查询的速度保证。`PlaceNew` 返回只说明交互放置已启动，不等于元件已落在图纸上。

含旧实例的工程读回为 U1、U2、U3、U4：旧 U1–U3 保留原来的大写 `PCB Footprint` 属性，新 U4 使用小写属性，四个实例均有 20 个引脚和正确型号。此项验证限定为这份独立工程副本。

## 四轮 API 提交的验证方法

1. 在独立工程中，经实际 Capture 内嵌 CEF 面板点击搜索、结果行和放置按钮，记录生产代码发回的 `place` 响应。
2. 测试脚本取消交互放置，再用官方 `PlacePart` API 在固定位置提交一个实例，赋予唯一位号并保存。位号由测试脚本赋值，这不属于产品自动标注验收。
3. 单独启动 Dbo 读取会话，重新打开已保存 DSN 和 OLB，检查实例数量、位号唯一性、型号、20 个引脚编号和 `PCB Footprint` 属性。新实例应使用实际小写 PSM 名称。

没有将上述 API 提交等同于真实鼠标点击落点。所有变更限于独立测试工程；已核对两个原始工程的 4 个 OPJ/DSN 文件，**4 / 4 的 SHA-256 均与测试前一致**。

## 用户实际鼠标放置（单独计数）

测试脚本通过真实 CEF 面板准备 `C2053170` 的交互放置；**用户本人在原理图画布点击落点，并直接回复已完成放置**。观察器发现独立工程实例数从 0 变为 1，随后结束连续放置并保存，没有调用 `PlacePart` 坐标提交或 `SetReference` 位号赋值。

| 核对项 | 结果 |
|---|---|
| 实例数 | 0 → 1 |
| 自动生成位号 | U1 |
| 型号 / 引脚 | STM32F031F6P7TR / 20 |
| PCB Footprint | `c2053170_tssop_20_l6_5_f2bd621e` |
| 保存后独立 Dbo 重开 | 通过，仍为 U1 / 20 引脚 / 正确封装属性 |

该案例覆盖了本机、这个元件的一次真实鼠标落点及自动位号。自动化截图和鼠标输入通道仍不可用，鼠标由用户执行；本轮键盘 Escape 曾成功。未将此结果扩展为截图视觉验收、所有元件或全部人工交互均已通过。

## 首次创建 OLB 专项

专项已完成四组对照：原路径在原编号属性和实验编号属性下均崩溃；官方归一路径在两种属性下均完成首次建库并返回 `PlaceNew`。原始编号属性组随后通过 API 提交、保存和独立读回；实验编号属性组在后续 repair OLB 的另一次放置中由用户鼠标落点并通过保存读回。

各组均从 0 OLB、0 integrity、0 实例、0 设计缓存开始；供应商和转换资源已在本地缓存。完整矩阵及提交方式边界见 [v0.49.1 专项报告](v0.49.1-capture-placement.md)及 [JSON](v0.49.1-capture-placement.json)。随后最终 v0.49.1 安装包也通过安装及全新 Capture 进程的生产插件验收：无 QA override，冷建返回、API 保存和独立读回通过。该安装版 API 验收实际位号为 U?，没有显式标注或新增鼠标落点验收；它与前述 QA 案例分别记录。

## 测试脚本回调查证

产品 `PlaceNew` 返回后，测试脚本的自动提交回调没有到达；外部 replay 驱动随后完成提交。静态检查发现 Cadence 的 hosted `nativeCall` 包装器会在 Tcl 命令末尾追加 `hostedClientId`，而 QA 的 `uiPlacementReturned` 原定义为零参数。产品请求处理器已有可选 `clientId` 参数。

在旧工程兼容案例中，仅将 QA 回调改为接收 `args`，实际桥接随后记录了 `ui_place_returned=1` 和 `hosted_client_argument_count=1`，确认漏接了一个宿主参数。这个测试脚本问题已定位；它不能用于解释更早的 `PlaceNew` 未返回或原生崩溃，也不需要据此修改产品放置代码。提交仍由外部 replay 驱动执行并独立读回。

## OLB 独立审计

旧、新 OLB 均为 51,712 字节；原生读取到的包、器件、符号、20 个引脚拓扑和顺序一致。官方 XML 导出只出现路径、时间戳和三处 PCB Footprint 大小写的差异，显式归一化这些字段后 XML 完全相同，读取前后原文件 SHA-256 不变。部分二进制差异未被 XML 表达，不能据此证明所有运行中设计缓存状态均有效。

## 仍未关闭的项目

- 初始带执行跟踪的诊断出现原生崩溃。Cadence XML 和 minidump 确认 `0xC0000005` 读取空地址 `0x0`，故障位于 `orDb_Dll64.dll + 0x253ea6`，报告符号为 `DboPlacedInst::DboPlacedInst + 646`。原转储证据保留，详见 [脱敏崩溃审计](v0.49.0-capture-crash-audit.md)。
- 后续无跟踪冷建对照及最终安装版验收已验证本机有效的官方 OLB 路径归一化修正；没有私有调试符号，未证明 Cadence 内部库对象管理的完整机制。不能将移除执行跟踪或弹窗视为充分修复；实际安装和生产插件结果见新报告。
- 用户已完成一次实际鼠标放置，完整人工交互与截图视觉验收尚未覆盖。
- [Allegro 10 轮测试](v0.49.0-pcb-placement.json)仍保留 8 成功、2 失败；Capture 的成功不覆盖这些偶发故障。
- 尚无 Capture 17.2 实机及独立干净客户环境验证。

报告只公开脱敏结果与本地证据文件的 SHA-256，不包含用户名、绝对路径、进程编号或供应方 CAD 文件。原发布的其他测试范围见 [v0.49.0 发布记录](../releases/v0.49.0.md)。
