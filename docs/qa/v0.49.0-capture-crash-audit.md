# Capture 崩溃只读审计（2026-11-12）

两份 Cadence 自带崩溃报告及 minidump 已确定同一个故障点：**0xC0000005 读取空地址 0x0，orDb_Dll64.dll + 0x253ea6**。报告显示 `DboPlacedInst::DboPlacedInst + 646`，上一帧为 `DboPage::NewPlacedInst + 247`。下文保留当时只读审计的范围与结论。

后续进展：[v0.49.1 冷建对照](v0.49.1-capture-placement.md)又复现两次无跟踪原路径崩溃；使用官方 API 归一化 OLB 路径后，原编号属性和实验编号属性两组均成功返回 `PlaceNew`。该实验支持本机有效的路径修正，不删除下面的历史失败，也未证明 Cadence 内部对象管理的完整机制。

时间采用 minidump 头的 UTC 时间转换为 +08:00，与文件修改时间一致。XML 时间字段与其差 8 小时，不把该字段直接标成 UTC。Windows Application 日志可以读取，但最近两天没有对应 Capture 记录；系统 WER/CrashDumps 的最近 Capture 文件是 11 月 9 日，未拿旧报告推断本轮故障。

中断线程栈包含 `TclNRRunCallbacks`、`TclChannelEventScriptInvoker`、`Tcl_NotifyChannel`，与当前产品的 `fileevent -> finish -> PlaceNew` 上下文一致。它证明调用上下文，不能证明 fileevent 或执行跟踪是根因。部分 Capture 符号的偏移很大，可能只是邻近导出符号，不能当作带私有调试符号的完整定位。

初始带跟踪的失败在 `buildOlb` 新建 OLB 后立即调用 `PlaceNew`；四轮成功复验使用缓存 OLB 且已换 Capture 进程。因此尚未单独控制执行跟踪、首次建库与宿主状态。后续实验应保持来源和 OLB 字节固定，分别记录首次创建后的放置与新会话读缓存放置，不能只以去掉跟踪后成功认定修复。

## 官方调用及参数

- 产品的 `PlaceNew <OLB> <package> 0` 与安装目录 `capPSpPartPick.tcl:69`、`capPSpiceSourceApp/tcl/capSourceAppBase.tcl:220` 的官方调用一致。两个生产 Tcl 文件与安装版 SHA-256 完全相同。
- 官方 `PSpiceModelAppCapture.tcl:247` 将第三参数命名为 `flag`。没有证据支持把它当成原生 `GetDesignator` 或设备索引并改为 -1。
- 当前 OLB 存在指定包名，原生审计为一个 package / device / logical part 和 20 个引脚。`GetDesignator=-1` 在旧成功库与当前库中相同。初始 `GetId` 检查未核对状态；后续检查返回 0 且状态失败，因此只能记为不可用，不能认定有效零 ID。
- 官方搜索面板另有 `PlacePartEx`：它使用独立的空 device-designator 参数及 `isConvert=0`。此接口位置参数不同，不能混用其参数含义来修改 `PlaceNew`。
- 会话日志中“找不到 OLB”之后有正常创建、保存记录，不能将首次建库前的文件不存在直接解释为放置时缺库。

本次只读取既有日志、转储、官方脚本与产品源码；未启动 Capture、改系统配置、二进制或生产代码。原始转储和 XML 含内存及环境信息，仅保留本地；[JSON](v0.49.0-capture-crash-audit.json) 只摘录异常、栈和证据 SHA-256。
